# 完善 plan/auto 模式

保持当前语义（plan = 规划+审批+执行，auto = 跳过规划直接执行），增强四个方面。按依赖顺序分 4 个阶段实现。

---

## 阶段 1：运行时模式切换

让 `skipPlan` 从启动时锁定变为每条消息独立可切换。

### `src/agent/Orchestrator.ts`
- 新增私有字段 `private skipPlan: boolean`（从 `OrchestratorConfig.skipPlan` 初始化）
- `submit()` 中的 `if (this.cfg.skipPlan)` 改为 `if (this.skipPlan)`
- 新增公开方法 `setSkipPlan(skip: boolean): void { this.skipPlan = skip }`
- 新增 `getSkipPlan(): boolean { return this.skipPlan }`

### `src/cli/commands/index.ts`
- 新增 `/plan` 命令（无参）：调 `ctx.setSkipPlan(false)`，返回 `已切换到 Plan 模式（规划→审批→执行）`
- 新增 `/auto` 命令（无参）：调 `ctx.setSkipPlan(true)`，返回 `已切换到 Auto 模式（跳过规划，直接执行）`
- `CommandContext` 新增 `setSkipPlan: (skip: boolean) => void`、`getSkipPlan: () => boolean`

### `src/index.ts`
- `commandContext` 新增 `setSkipPlan: (skip) => orchestrator.setSkipPlan(skip)`、`getSkipPlan: () => orchestrator.getSkipPlan()`

### `src/tui/App.tsx`
- 状态栏（顶部 `commandContext.getModel()` 行）追加模式标记：`[Plan]` 或 `[Auto]`，通过 `commandContext.getSkipPlan()` 判断。`setRenderTick` 已在斜杠命令后触发，会刷新显示。

## 阶段 2：计划审批与重规划

### `src/agent/types.ts` — 新增事件
```ts
| { type: 'plan_approval_request'; plan: Plan }
```
携带完整 Plan（summary + todos + filesToModify + estimatedSteps），替代当前只传 summary 的 `tool_approval_request`。

### `src/agent/Orchestrator.ts` — `planAndExecute` 重构
当前（346-352 行）：
```ts
this.setPhase('awaiting_approval')
const approved = await this.cfg.requestApproval('plan', { plan: plan.summary })
if (!approved) return '计划被拒绝...'
```
改为**重规划循环**：
```ts
let currentPlan = plan
let replanAttempts = 0
const MAX_REPLAN = 3

while (replanAttempts <= MAX_REPLAN) {
  this.setPhase('awaiting_approval')
  // 发送完整计划到 TUI 审批
  const feedback = await this.requestPlanApproval(currentPlan)
  if (feedback === 'approve') break          // 批准 → 执行
  if (feedback === 'reject') {               // 彻底拒绝 → 丢弃
    return '计划被拒绝。请重新描述你的需求。'
  }
  // feedback 是用户反馈文本 → 带反馈重规划
  replanAttempts++
  if (replanAttempts > MAX_REPLAN) {
    return '已达到最大重规划次数(3)。请重新提交需求。'
  }
  this.setPhase('planning')
  currentPlan = await planner.replan(userInput, messages, currentPlan, feedback)
  this.todos = currentPlan.todos
  this.emit({ type: 'todo_update', todos: this.todos })
}
return await this.runExecutor(currentPlan, messages)
```

新增 `requestPlanApproval(plan: Plan): Promise<'approve' | 'reject' | string>`：
- 非交互模式返回 `'approve'`
- 交互模式：复用 `globalThis.__nexusApprovalResolve` 机制，但 emit `plan_approval_request` 事件（携带完整 plan）。返回值：`true`→`'approve'`，`false`→`'reject'`，字符串→反馈文本。
- 需要扩展 `requestApproval` 机制支持返回字符串而非仅 boolean。为此新增一个独立的 plan 审批 resolver（避免破坏现有 tool 审批的 boolean 契约）。

### `src/agent/Planner.ts` — 新增 `replan` 方法
```ts
async replan(userRequest, messages, prevPlan, feedback): Promise<Plan> {
  const replanMessages = [...messages, {
    role: 'assistant',
    content: JSON.stringify(prevPlan, null, 2),
  }, {
    role: 'user',
    content: `用户对计划的反馈：${feedback}\n请根据反馈调整计划，输出新的 JSON 计划。`,
  }]
  // 复用 plan() 的 ReAct 探索 + parsePlan 逻辑
  ...
}
```

### `src/tui/App.tsx` — 计划审批 UI
- 新增 state `planApproval: { plan: Plan; resolve: (result: 'approve'|'reject'|string) => void } | null`
- 新增 `plan_approval_request` 事件处理器：从 `globalThis.__nexusPlanApprovalResolve` 取 resolve，设 `planApproval`
- 新增组件 `PlanApprovalPanel`（或内联渲染）：展示 summary、todos 列表（带序号）、filesToModify。快捷键：`[Y] 批准` `[N] 拒绝` `[F] 输入反馈重规划`。选 F 时进入文本输入模式，Enter 提交反馈文本。
- `InputBox` 的 `disabled` 追加 `|| !!planApproval`

### `src/index.ts`
- 新增 plan 审批 resolver 机制（`planApprovalResolver` + `globalThis.__nexusPlanApprovalResolve`），与 tool 审批并行。

## 阶段 3：计划生成与 todo 进度修复

### `src/agent/Planner.ts` — 用工具调用替代 JSON regex
- `PLAN_SYSTEM_SUFFIX` 改为指示 LLM 在探索完成后调用 `submit_plan` 工具提交计划（而非输出 JSON 代码块）
- 新增 `submit_plan` 工具（`src/tools/submitPlan.ts`，`phase: 'plan'`，`requiresApproval: false`）：schema 接收 `{ summary, todos: [{id,content}], filesToModify, estimatedSteps }`，execute 时将参数存入模块级 `pendingPlan` 变量
- `Planner.plan()` 改为：ReAct 循环直到检测到 `submit_plan` 工具调用 → 从 `pendingPlan` 读取结构化计划 → 返回。不再用 `parsePlan` regex。
- 保留 `parsePlan` 作为兜底（若 LLM 未调用工具而是输出 JSON 文本）

### `src/agent/Executor.ts` — 修复 todo 进度启发式
当前 `updateTodoProgress`（363-381）有两个问题：
1. bash 含 "test" 时反而不完成 todo（逻辑反了）
2. 与 LLM 的 `update_todo` 工具双重写入冲突

修复方案：
- **移除 Executor 的 `updateTodoProgress` 中的 bash 完成启发式**（373-380 行删除）。todo 完成完全交给 LLM 通过 `update_todo` 工具控制（`complete` action）。
- 保留 `edit_file` → 标记 `in_progress` 的启发式（这个是合理的，因为 LLM 常忘记标记开始）。
- `EXECUTE_SYSTEM_SUFFIX` 新增明确指示：`每完成一个步骤，调用 update_todo(action="complete", id="...") 标记完成`。

### `src/agent/Orchestrator.ts` — auto 模式轻量 todo
当前 `executeDirectly`（359-368）合成单个假 todo = 原始 prompt。
改为：不再合成假 todo，而是给 Executor 传空 todos + 在 prompt 中指示"自主拆解任务为 todo"。Executor 的 ReAct 循环中 LLM 会通过 `update_todo(action="add")` 自主添加步骤。
```ts
private async executeDirectly(userInput, messages) {
  const plan: Plan = {
    summary: userInput,
    todos: [],  // 空，让 LLM 自主拆解
    filesToModify: [],
    estimatedSteps: 0,
  }
  this.todos = []
  return await this.runExecutor(plan, messages)
}
```
`EXECUTE_SYSTEM_SUFFIX` 新增：`Auto 模式下，如无预设 todo，请先用 update_todo(action="add") 拆解任务为 2-5 个步骤，再逐步执行。`

## 阶段 4：执行后验证阶段

利用当前闲置的 `verifier` ModelRole，在 Executor ReAct 循环结束后新增验证。

### `src/agent/Executor.ts` — 执行后验证
`execute()` 方法末尾（ReAct 循环结束后、return 前）新增：
```ts
// ─── 验证阶段 ───
if (this.todos.some(t => t.status !== 'complete')) {
  this.config.onEvent({ type: 'phase_change', phase: 'verifying' })
  const verifyResult = await this.runVerification(plan, result)
  if (verifyResult) result += `\n\n## 验证\n${verifyResult}`
}
```

新增 `runVerification(plan, executionResult)`:
- 用 `verifier` 角色模型（`getRouteInfo('verifier')`），但当前 Orchestrator 未传 verifier route。
- 简化方案：复用 executor 模型，构造一个验证 prompt：`检查以上修改是否完成所有 todo，运行测试验证，输出验证结论`。允许 verifier 使用 `bash`（跑测试）和 `read_file`（检查改动），但不允许 `edit_file`（只读验证）。
- 用单轮 `generateText`（非 ReAct 循环），maxSteps 限制为 3-5（验证应快速）。
- 返回验证结论文本。

### `src/agent/Orchestrator.ts`
- `runExecutor` 中向 Executor 传入 verifier 相关配置（或 Executor 内部通过新 config 字段获取 verifier model）。
- 简化：Executor 直接复用自身 model + toolRegistry 做 verification，无需新 route。

### `src/tui/App.tsx`
- `phaseLabel` 中 `verifying: '验证中...'` 已存在（226 行），无需改动。验证阶段的 `phase_change` 事件会自动更新状态栏。
